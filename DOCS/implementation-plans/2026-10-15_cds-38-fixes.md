# Implementation plan: CDS-38 fixes, the signed-off review findings

**History of this plan.** The CDS-38 review reported 14 Blockers, 48 Changes and 26 Notes (record `.review/2026-10-14_cds-38-independent-review.md`, merged in #76). The owner signed them off on 2026-10-15 (section 5 of the record): all 14 Blockers, 47 of 48 Changes and 17 Notes are to be fixed; 5 findings are deferred and 5 need no action. The CDS-38 plan (step 6) requires the fixes in small pull requests before P3, a specification pull request first where a specification is wrong, and a plan addendum before any fix that is more than a correction. This is that plan. The owner approved it on 2026-10-15.

**Goal.** Put right everything the owner accepted, so that the API flags, the harness and the Phase 4 UI have no known Blocker or Change before the 23 UI flags (P3 and P4) are built on them, and prove each fix the way the review found the fault: a test or check that is red on the unfixed code and green on the fixed.

## Evidence gathered before planning

Read-only; nothing was changed. The sign-off table (record section 5) gives every accepted finding a slice; the verification (record section 4) gives, for most, a probe that already shows the fault.

| Finding | Consequence for the plan |
|---|---|
| 12 of the 14 Blockers and most Changes were reproduced by a mutation, a live request or a short test; the working tree was clean after each | Each fix reuses its reproduction as the test that must go red first (specification first, test first) |
| The validator (B-01, B-10, B-11) is what every API scenario passes through; the service fixes would be checked by it | The validator is fixed first (F2), so later service fixes are judged by the stricter check |
| Several findings change a contract or a specification (A-15 example order, A-16, A-17, A-09 and A-11 flag text, B-10 closed schemas, C-07, C-08, B-20, A-28, A-29) | One specification slice (F1) comes first. It is the only slice that changes the contract |
| B-14 and B-15 need a persona with a closed account that has a stored balance; fixtures feed the service tests, the harness and the UI tests | The fixture change (F5) goes after the service rules and before the service tests that read it (F6) |
| The flag proof (F7) depends on the flags as fixed in F4 | F7 follows F4 |
| C-16 to C-19 (README counts, statuses, headers) go stale with every slice | Done once, last (F12), so the figures are true when written |
| C-23 (CI time limit) is a forecast; C-26, A-24 belong to P4; A-22 is low risk | Deferred, each to a named place |

## Scope

Fixing, in the repository, the findings the owner accepted. The 62 Blockers and Changes and the 26 Notes are listed with their slices in section 5 of the record; this plan does not repeat the table, only groups it.

**Out of scope.** The deferred findings (C-23 to P5, A-24 and C-26 to P4, A-22 to the backlog, B-22 to the confirmation pass); the five Notes with no action; the Phase 5 slices P3 to P7 themselves; any change the owner has not accepted.

## Steps

Twelve slices, one pull request each, in this order. Each branch is `claude/cds-38-fix-<topic>`. Each is merged only on the owner's word and after its own CI run (`verify` and `ui`). The number of tests changes as slices land; each pull request states the new counts.

**F1. Specifications and the contract (documents only).** Specification first. Contract v18, `info.version` 0.9.5.
- A-15: correct the contract example to oldest first.
- A-16: BR-14 says `percent` has at most two decimals, in the specification and the cases.
- A-17: a month after the current month is never Missed, in the rule, its cases and the year status.
- A-09 and A-11: read the contract's flag text for `currency-float` and `excluded-in-total`; where the code differs the code follows the text (F4); where the text is wrong or silent it is narrowed. Each decision is recorded in the slice.
- B-10: read the response schemas; add `additionalProperties: false` where the specification says the shape is closed, and list any response that stays open and why.
- C-07 (the gauge stays a progressbar), C-08 (`/debug`), B-20 (the harness design says what is built), A-28 and A-29 (one sentence each).
- Checks: `npm run verify` 14 of 14 (contract lint, fixtures, Gherkin, client, Schemathesis run as in CI).
- Risk: closing the schemas (B-10) could fail the service. That is the point; F2 and F3 repair what it exposes. If a closed schema breaks more than a correction (many service changes), it is split out and an addendum is written first.

**F2. The harness validator and hooks.** B-01 (content type checked), B-09 (`Retry-After`), B-10 (strict mode), B-11 (Problem `status` agrees, no `stack`), B-12 (headers returned, wording corrected), B-13 (diagnostics attached, state restored by the hooks), B-21 (readable failure for a missing body), B-23 (parallel runs refused).
- Test first: a validator test for each case (a `text/plain` Problem, an extra property, a Problem whose `status` disagrees, a `stack`).
- Expect the 59 `@api` executions to expose service faults. Each is recorded and fixed in F3 or F4; if one is outside this plan, it is written up and the owner decides.

**F3. Service faults and the edge.** A-01 and A-02 (one fault handler: every unhandled exception is a Problem in every profile, the trace only in the log), A-03 (the gate treats repeated slashes and equivalent forms as the same path), A-05 (`X-Correlation-Id`: echo a valid supplied value, else generate; with its tests), A-06 (the clock parses strictly to date-time), A-07 (year window checked before the bureau), A-08 (test-control errors are always Problems), A-18 (clock lock), A-20 (no-store on `index.html`, 404 under `/assets/`).
- Test first: each with its reproduction (`verify_live.py` forms become service tests).
- Probe: re-run the CDS-38 live script against the fixed build, with the same inputs, and record the result in the pull request.

**F4. Service rules and flags.** A-04 (resend check-and-record made atomic; a parallel-burst test), A-09, A-10, A-11 (flag reach, as decided in F1), A-16 and A-17 (the rules, as specified in F1), A-21 (one source for email status), A-23 (rune-aware letters).
- Test first: each. The BusinessRules library changes only for A-16, A-17 and A-23, never for a flag (a flag changes a call site, DR-064).
- Check: `npm run check:bug-flags` unchanged (8 of 8 implemented flags caught) before F7 tightens the proof.

**F5. Fixtures and the steps that read them.** B-14 and B-15 (a persona with a closed account that has a stored non-zero balance, so the check can fail), B-04 and B-19 (exact comparison), B-05, B-17 and B-18 (expected values from the persona fixture, every sensitive profile value), B-16 (the named card).
- Proof: each step is shown red against a mutated service or page, as the review did (P2, P3, P12, P13 in the reports), then green.
- Risk: a fixture change moves service tests and UI tests that read the persona; the slice runs all of them.

**F6. Service tests.** A-12 (cross-user refusal on the account, history and balance routes), A-13 (assert the set-up), A-14 (four tests that assert the code), A-19 (the suffixes), A-25, A-27.
- Proof: re-run the review's mutation for each (A-12's dropped ownership check must now turn a test red).

**F7. The flag proof.** B-02 and B-03 (a catch counts only for the stated failure: `failsWith` specific, and absent from the run without the flag), B-06 (the off run asserts an empty flag list), B-07 (an on run counts only if something ran), B-08 (per-run timeouts, SIGTERM stops both instances), B-26 (exact name match).
- Test first: negative probes that the review used (a flag credited for another failure; a harness bug that fails everything) must give "not caught" or "caught for another reason".
- Check: `check:bug-flags` still reports 8 of 8, now for the stated reasons.

**F8. UI redirects and stale responses.** C-01, C-20 (one guard: resolve against the origin and accept only the same origin; `LoginPage` uses it), C-04 (the dot-segment and backslash cases in the component table and, specification first, in the Gherkin scenario), C-03 (a response whose request is no longer current is ignored, in every fetching hook, with a delayed-answer test each), C-22 (a way back on a page past the end).
- Probe: the five dot-segment inputs from the record return a same-origin path; the `@ui` redirect scenario runs with a dot-segment address.

**F9. UI display and semantics.** C-02 (real `aria-valuenow`, raised `aria-valuemax`, the fill capped), C-05 (over-limit badge hook and colour bands as specified), C-06 (`search-list` hook), C-21 (initials fallback), C-25 (the page behind the open drawer is inert), C-27, C-28 (a landmark on the detail header), C-30 (guarded storage write), C-32 (formatted months), C-33 (attempts shown after the first wrong code).
- Specification first where the specification needs a sentence; tests with each; the glossary hooks updated.

**F10. Build, exit checks and CI.** C-13 (a build check that fails if the public `dist` holds test-build markers, run in `verify` and the `ui` job), C-29 (the test build goes to `dist-test/`; harness logs named per run), C-09 (every route and listed state is scanned), C-10 (axe in both themes), C-11 (wider text applied so `rem` sizes follow), C-12 (the `aria-pressed` state asserted, or the stated catch narrowed), C-14 (actions pinned to commit SHAs with the version in a comment; the Redocly tool in the lockfile), C-15 (`AfterAll` timeout and a printed reason).
- Proof: re-run the three exit-check mutations from the record (a 375 px break, a dark-theme colour, `aria-pressed` removed); each must now be found. For C-13, re-run the unset-variable mutation; the check must fail.
- Risk: pinning actions needs the SHAs for each action at its current major version; they are looked up once and listed in the pull request. No new dependency except moving an existing tool into the lockfile.

**F11. Confirmation pass (decision D4).** One fresh-context read-only reviewer, as the review, with its prompt recorded verbatim and hashed, reading the fixes and what they could have broken, and the areas the review covered thinly: the harness validator, the Gherkin store, the generated contract; `check:schemathesis`, `check:service-contract`, `exit-checks.ts`, the full `@ui` run; and B-22 (a random-order run). Reports Blocker, Change, Note; the author verifies; the owner signs off. A different model from the first review is preferred; the owner is asked which before launch (decision D2 below). Any new Blocker or Change is fixed before F12.

**F12. Records.** The README, specification headers and scope statements brought up to date with figures counted at that point (C-16 to C-19); the implementation log; this plan's Outcome; a decision register entry on what CDS-38 found and what it changes in the exceptions in DR-058 and DR-063; backlog (CDS-38 Done; CDS-41 unblocked); CHANGELOG; Kanban. The portfolio-root handover and registry are updated when the owner asks.
