# Implementation plan: CDS-29, Phase 4, the React UI

**History of this plan.** Presented in full to the owner on 2026-10-12 after a read-only spike, with six decisions put in decision brief 11 (all answered: D1, D2, D4 and D6 explicitly, D3 and D5 as recommended). This file is the plan as written for approval.

**Goal.** Build the React UI to the UI specification and make all 41 `@ui` scenarios (11 feature files) pass, against the live service, with an axe-core scan of every page clean. This is the Phase 4 exit gate (README 'SDD workflow'): *all `@ui` scenarios green against the mock and live; axe-core zero violations with flags off*, as amended by decision brief 11 D1 (the mock is replaced by the live service for the scenarios).

## Steps

Specification first. Seven pull requests, each merged in order on the owner's word and its own CI run.

**S0, specification (this plan's pull request).** The plan, decision brief 11 (D1 to D6), DR-062, UI specification v13 (principle 2; hosting; the verification table), backlog v53 with the slice tickets CDS-31 to CDS-36.

**U1 (CDS-31), foundation.**
1. `demo-apps/demoapp001-react-ui/` (own `package.json` and lock, D3): React, Vite, TypeScript, Vitest and Testing Library pinned exactly; the router proven here; strict `tsc`.
2. App shell: demo banner, layout and themes, formatting helpers (UI specification 4.2), `SectionState` (4.3), the generated client wired by base URL, the token in memory.
3. Service: serves the built UI from `/` beside `/api/v1` (D2); API specification v25; service tests.
4. Harness: Serenity/JS 3.49.0 and Playwright 1.64.0 together; a `BrowseTheWeb` ability; a `ui` profile and UI steps in the existing package (D5); the runner builds the UI and starts the service with test control; the login scenarios (3) green.
5. CI: a separate `ui` job (D4): install, typecheck, Vitest, build, the `@ui` scenarios. `verify` gains the UI typecheck, tests and build only if they stay cheap.

**U2 (CDS-32), report overview (5 scenarios).** Score and history chart (hand-built SVG with a table alternative), changes list and toggle (fetches every change, DR-047), summary feedback, chat drawer (component-tested), next-update text.

**U3 (CDS-33), report pages (14 scenarios).** Payment history (3), report changes (4), searches (3), personal details (2), debt overview (2).

**U4 (CDS-34), accounts (9 scenarios).** Account-type lists and totals, closed accounts, account detail, the detail edit form with the BR-14 copy, the open-redirect guard (`security/open-redirect.feature`).

**U5 (CDS-35), profile (10 scenarios).** My profile, preferred name, the email sub-page (section 4.2) and mobile sub-page (4.1); no profile data in titles or URLs (PR-08).

**U6 (CDS-36), exit.** axe-core on every page with flags off (zero violations); the three layouts (375, 768, 1280 px); the full `@ui` run against the live service; records and a Phase 4 gate decision brief.

Each UI slice adds its page's component tests (the four states of 4.3) and its step definitions, and each ends with its scenarios green, so the 41 are reached as 3, 8, 22, 31, 41.

## Verification

- Every slice: the project's `verify` and the `ui` job pass locally and in the pull request's own CI run, with counts and durations as measured.
- Probes that must fail, reverted afterwards: a hook renamed in the UI (the scenario goes red); a page that reads a figure from the wrong field (the assertion fails); the open-redirect guard removed (the security scenario fails); a missing `aria` name (axe-core reports it, in U6).
- Exit: 41 of 41 `@ui` scenarios green against the live service; axe-core zero violations on every page; the 59 `@api` scenarios still green.
